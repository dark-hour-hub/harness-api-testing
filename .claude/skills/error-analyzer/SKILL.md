# 测试失败分析器

从测试报告、测试脚本和用例定义三个维度交叉分析，找出通过率低的共性根因，并给出用例生成器的修复建议。

## 输入来源

启动时先探查当前项目的实际目录结构，定位以下数据源（路径可能因项目而异）：

| 数据源 | 定位方式 | 内容 |
|--------|----------|------|
| 测试报告 | 搜索 `report/` 目录下的 `.xml` 结果文件（通常为 `*.xml` 或 `results_*.xml`） | 测试框架输出的结构化失败详情 |
| 测试脚本 | 搜索 `generated/` 或测试输出目录下的测试文件 | 测试函数、参数化数据 |
| 框架代码 | 定位测试脚本目录下的 `conftest.py` 和工具模块（如 `api_utils.py`、`helpers.py`） | 请求构建、断言逻辑、认证流程、默认值 |
| 用例定义 | 搜索用例目录（如 `*-testcases.yaml`、`testcases/`、`cases/`）下的 YAML/JSON 定义文件 | 用例的预期断言值、请求参数 |

若上述数据源缺失，先向用户确认路径再继续。

## 输出

| 文件 | 路径 | 内容 |
|------|------|------|
| 错误分析报告 | `{workflow_dir}/04-results/error-analysis.md` | 分类汇总的失败根因分析 |
| 修复建议 | `{workflow_dir}/04-results/repair.md` | 针对用例生成器的改造方案 |
| 补充建议（可选） | `{workflow_dir}/04-results/suggestions.md` | 框架、流程、CI 等其他建议 |

## 分析流程

### 步骤 1：汇总测试结果

读取所有测试报告 XML 文件，提取：

- 每个模块/文件的总用例数、通过数、失败数、通过率
- 汇总表：按模块 + 按错误类型两个维度
- 识别 **全模块覆灭**（通过率接近 0%）的模块 — 通常是基础设施或公共依赖问题

### 步骤 2：分类错误模式

从测试报告中提取所有失败用例的错误消息和堆栈，按以下维度归类（以下为通用分类框架，具体类别由实际报告中的错误决定）：

#### 类别 P0：基础设施错误 — 导致整个模块/大批量用例失败

**识别特征**：同一模块内几乎所有用例因同一原因失败。

**常见根因方向**（根据实际错误判断，不限于此）：
- 认证 token 提取失败：检查框架代码中 token 提取路径的默认值与 API 实际返回的 JSON 键名是否一致（特别注意驼峰 vs 下划线命名差异）
- 公共依赖注入失败：如 fixture 加载报错、前置条件不满足
- 服务不可达：检查 base_url / 环境配置是否正确
- 配置缺失：检查用例定义中的公共配置段是否缺少关键字段

**检查方式**：
1. 对比框架代码中相关字段的**默认值**与 API 实际返回的**字段名**
2. 对比同模块 YAML 中该字段是否显式配置
3. 确认是"配置缺失"还是"配置值与实际不符"

#### 类别 P1：请求数据与接口契约不匹配

**识别特征**：大量用例因参数校验失败，但实际错误消息与预期的错误消息不一致。

**常见根因方向**：
- 请求体缺少必填字段：检查 `global_headers` 或公共配置中引用了哪些变量（这些变量通常需要出现在请求体中），用例是否都传了
- 校验顺序与预期不符：接口对参数的校验有先后顺序，先校验的字段失败会"掩盖"后续字段的校验
- 校验消息拼接模式与断言模式不匹配：接口返回多个字段的错误拼接，但用例断言用了精确匹配

**检查方式**：
1. 列出 `global_headers` 中引用的所有变量 → 确认每个需要这些变量的接口的请求体都包含对应字段
2. 对比实际校验错误消息和预期消息 → 判断是否存在"校验顺序覆盖"
3. 检查 `validation_message_mode` 配置值与实际返回格式是否匹配（拼接 vs 单个）

#### 类别 P2：预期值与实际响应不匹配

**识别特征**：单个或少量用例因断言值不符而失败，业务逻辑本身正常。

**常见根因方向**：
- `business_message` 值不准确：生成器使用了默认/统一的消息文本，但不同接口（甚至同一接口的不同分支）返回不同消息
- `business_code` 值不准确：接口实际返回的业务码与预期不同（如预期 401 但返回 500，因为请求提前在校验层被拦截）
- `response_structure` 判断错误：接口返回的 data 结构（分页/列表/单对象/空）与断言中的 `data_exists` 字段不匹配
- `auth_probe_code` 未被使用或探测结果不准确

**检查方式**：
1. 从报文中提取实际值，与 YAML 预期对比
2. 追溯源码确认接口的实际返回逻辑
3. 检查 `response_structure` 的判断依据是否正确

#### 类别 P3：环境依赖不可用

**识别特征**：涉及外部服务（短信/邮件/第三方/存储等）的接口返回 500 或服务异常。

**常见根因方向**：
- 外部服务在测试环境未开通
- 第三方配置缺失或凭证过期
- 依赖的中间件（消息队列、缓存等）不可用

**检查方式**：
1. 确认 A7 环境能力探测是否已执行
2. 确认探测结果是否已反映到用例预期中（不可用的服务应调整预期为 skip 或 500）

#### 类别 P4：用例定义格式错误

**识别特征**：用例在发送请求前即报错（非 HTTP 层错误），堆栈指向框架代码的数据结构访问。

**常见根因方向**：
- YAML/JSON 中某字段类型不对（期望 list of dict 但写成了 list of str）
- 必填字段缺失或为 null
- 变量引用语法错误

**检查方式**：
1. 定位堆栈中报错的具体行
2. 检查对应 YAML 字段的实际数据结构
3. 与正常通过的用例对比该字段的写法

### 步骤 3：提取共性根因

按分类结果，归纳共性根因（不要逐用例罗列，按错误类型归纳）：

```markdown
## 共性根因

### 根因 1: {名称} — 影响 {N} 模块 / {M} 条用例 ({X}%)
- **症状**: 描述具体表现
- **直接原因**: 是什么导致了症状
- **深层原因**: 用例生成器为什么会产生这个错误
- **涉及范围**: 列出受影响的关键模块或用例 ID
```

### 步骤 4：交叉验证

对每个归纳出的根因，须同时验证三种数据源的一致性：

| 验证维度 | 数据来源 | 关注点 |
|----------|----------|--------|
| 实际行为 | 测试报告中的响应体 | 接口「实际返回了什么」 |
| 预期行为 | 用例定义中的 expected | 用例「期望返回什么」 |
| 默认行为 | 框架代码中的默认值/fallback 逻辑 | 框架在配置缺失时「默认做了什么」 |

三者对照，确认根因判断无误。若三者指向不一致，说明分析有遗漏，需重新检查。

```markdown

> 生成时间: {当前时间}
> 数据来源: {测试报告目录路径}

## 总体情况

| 模块 | 总用例 | 通过 | 失败 | 通过率 |
|------|--------|------|------|--------|
| ... | ... | ... | ... | ...% |
| **合计** | **...** | **...** | **...** | **...%** |

## 错误分类汇总

### 类别: {错误类别名}（P{0-4}，影响 {X} 模块，{Y} 条用例）

**症状**: 描述该类错误的共同表现

**根因**: 分析深层原因（不要停留在表象）

**典型示例**（2-3 个）:
- 用例 XXX：期望 {A}，实际 {B}
- 用例 YYY：期望 {C}，实际 {D}

**修复方向**: 概述解决思路

### 类别: ...

## 未归类的独立错误

对无法归入以上类别的偶发或孤立失败，简要列出。
```

### 步骤 6：输出 repair.md

针对用例生成器的改进建议。聚焦于能从根源上减少上述错误：

```markdown
# 用例生成器改进建议

> 基于 error-analysis.md 的根因分析

## 高优先级（直接导致大量失败）

### 1. {改进项标题}

**关联错误**: 对应 error-analysis.md 中的 {类别名}

**现状**: 当前生成器的行为

**改进方案**: 具体怎么改

**涉及改动**: 生成器的哪个阶段 / 哪个步骤 / 哪个文件

### 2. ...

## 中优先级（影响部分用例）

### ...

## 低优先级（锦上添花）

### ...

## 改动影响评估

| 改进项 | 预计减少失败数 | 改动范围 | 风险 |
|--------|---------------|---------|------|
| ... | ~N 条 | 低/中/高 | 描述潜在副作用 |
```

### 步骤 7：输出补充建议（如有）

如果发现测试框架、执行流程或 CI 层面的改进空间，写入 `suggestions.md`。例如：
- 框架代码增加防御性校验（如对 YAML 数据结构的类型检查）
- 默认值策略调整（默认值应偏向"安全"而非"便利"）
- 增加 YAML schema 校验或 pre-commit hook
- CI 中增加环境可用性预检步骤

如果没有额外建议，跳过此步骤。

## 分析原则

- **不逐条罗列**：按错误类型归类，每类给 2-3 个典型示例即可
- **追根因不追表象**：不满足于"XX 不匹配"，追问为什么生成器会产生不匹配的值
- **影响面量化**：每种错误类型标注影响模块数和用例数
- **优先级排序**：先修影响面大的基础设施/公共配置问题，再修个例
- **可操作性**：每个改进建议必须具体到改哪个阶段、哪个步骤、哪个检查点
- **证据驱动**：每个结论必须有报告报文 + 用例定义 + 框架代码三者的交叉验证支撑
