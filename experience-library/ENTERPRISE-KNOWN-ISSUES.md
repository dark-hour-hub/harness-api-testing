# 企业级测试经验库（Enterprise Known-Issues）

> **用途**：所有项目执行前/中必须吸取的**通用经验** —— 测试工具链、脚本、框架、环境、方法论层面的坑。
> **维护**：由 `post-run-analysis` skill 在用户确认后回写；其余项目直接复用。
> **读法**：任何项目执行测试前，先对照本库检查执行环境与用例写法。

---

## 一、测试框架 / 生成器层面

### 1. pytest-bdd（8.x）步骤注册机制：动态 import 的模块不被扫描
- **现象**：`StepDefinitionNotFoundError`，即使步骤文件已被 `importlib.import_module` 导入（代码确实执行了，有 sentinel 为证）。
- **根因**：pytest-bdd 8.1.0 步骤定义按 **fixture 机制**注册，fixture 只在 conftest / 测试模块收集时注册；运行时动态 import 的模块不会被 fixture manager 扫描。
- **规避**：步骤必须内联写在 `conftest.py` 或测试模块内；扩展步骤要改 **template/conftest.py**（持久化），不要依赖"模块注册"。
- **教训**：升级主版本 pytest-bdd 后，旧步骤组织方式可能失效，升级前查 changelog。

### 2. 报告断言字段/文案要以"运行时真实响应"为准，不要凭文档/猜测
- **现象**：断言 `data.valid=true`（字段根本不存在）、断言 `新增测试用例`（实际标题是「新增评测用例」）—— 整段用例稳定失败且看不出原因。
- **规避**：写断言前先用 curl / probe 打一次接口或打开页面取真实结构；校验接口响应契约（REST 返回报文、表单标题、toast 文案）。
- **教训**：接口文档 ≠ 实现；错误堆栈常只显示断言失败，不暴露"字段名/文案不存在"。

### 3. 业务异常的包装器可能吞掉错误 data
- **现象**：接口返回 400 + `data:null`，错误详情丢失，无法定位。
- **根因**：控制器未注册对应的 `@ExceptionHandler`（如 `SchemeValidationException`），被全局 `BusinessException` 处理器兜住，data 恒为 null。
- **规避**：当"错误码明确但 data 为 null"时，去源码查该异常的 handler 注册情况；必要时读后端日志（traceId 定位）。
- **教训**：看响应体猜根因会走弯路；优先查异常处理器 + 日志。

### 4. 断言通过/文案类检查用 `get_by_text` 时注意作用域
- 见 UI 章节第 2 条（卡片级定位）。

## 二、JMeter / 压测层面

### 5. JMeter 唯一编码函数的坑（高并发写场景）
- **现象**：写入类压测（agent/testcase/scheme 创建）错误率飙升，全是 409/400。
- **根因**（实测三种方案的错误率）：
  | 方案 | 实测表现 | 原因 |
  |------|---------|------|
  | `${__threadNum}_${__iterationNum}` | 同线程全 409 | duration/loops=-1 模式下 `__iterationNum` **不递增** |
  | `${__Random(100000..999999)}` | 2~13% 409 | 8 万+采样在 90 万空间碰撞概率 ≈ c(n,2)/9e5 不可忽略 |
  | `${__counter(true,)}` | 98% 409 | 多线程下行为不可靠 |
  | `${__RandomString(12, A-Z0-9)}` | **0% 冲突** | 36^12 空间，碰撞可忽略 |
- **结论**：JMeter 写场景唯一编码统一用 `__RandomString(12,A-Z0-9)`；不要用 `__Random` 固定区间或 `__iterationNum`。

### 6. 压测写操作污染读操作基线
- **现象**：列表查询场景（同库先后跑写场景后）p95 从几百 ms 恶化到几十秒、rps 骤降。
- **根因**：写入场景分钟级积累几十万行，分页 count+排序变慢。
- **规避**：`先读后写`排序；或写入场景前清库；性能报告须注明库内数据规模。
- **教训**：性能基线的有效性依赖"被测数据规模"的可比性，写场景要计数并清理。

### 7. Windows 子进程输出解码（jmeter / 任意 CLI）
- **现象**：`UnicodeDecodeError: 'utf-8' codec can't decode byte ...`（在工作线程 reader 中崩溃）。
- **根因**：`subprocess.run(..., text=True)` 用系统 locale 编码（中文 Windows = GBK/cp936）解码工具的 UTF-8 输出。
- **规避**：`subprocess.run(..., encoding="utf-8", errors="replace")`。

### 8. 独立运行 / 无 manifest 时的场景 id 推断
- **现象**：`--jmx-dir` 单独跑时"无有效样本"，统计全空；实际是 jmx 内 sampler label 与推断 id 不匹配。
- **根因**：用了 `os.path.splitext(文件名)`（小写）当 scenario id，实际 label 是大写场景 id。
- **规避**：场景 id 从产物自身提取（解析 `HTTPSamplerProxy` 的 `testname`），不要从文件名推断。

### 9. Windows 压测客户端的端口耗尽（BindException）
- **现象**：`java.net.BindException: Address already in use: connect`，高并发短连接时大量出现。
- **根因**：Windows 动态端口范围有限（约 16k），大量 TIME_WAIT 堆积 → 客户端连接失败（**非被测系统问题**）。
- **规避**：降低并发、缩短 duration、必要时提升动态端口范围（需管理员）；报告中标注为压测机限制。

## 三、测试数据 / 环境层面

### 10. 状态类唯一约束的残留污染（"先清理后重跑"）
- **现象**：重跑同一套件时，大量 409 "xxxx already exist" / 唯一键冲突。
- **根因**：带唯一约束（如 code+version、code 唯一）的表，上一轮运行的数据未清理；且部分历史状态（如 ARCHIVED）**无删除 API**，物理删除只能走 DB。
- **规避**：任何可重跑套件必须配"清理脚本"（保留种子/金丝雀，只删运行期数据）；重跑前必执行。
- **教训**：写用例时先查清"哪些约束不可逆/不可删"，把清理做成流程的一部分而非事后补救。

### 11. 种子/金丝雀数据不可被测试破坏
- **现象**：一个用例把基准数据改坏（如把 agent `enabled` 置 0 / 删除），后续所有依赖它的用例连锁失败，且发生在距上游用例很远的脚本里，难排查。
- **规避**：破坏性用例必须作用于**自建数据**（作用域隔离），或**自愈**（执行后恢复）；禁止对种子数据做写操作。
- **教训**：UI 点击"删除/编辑"时，若未限定目标会命中种子卡片；要按"容器+唯一标识"精确定位（见下条）。

### 12. UI 定位：无 aria-label 控件用 data-testid；点击要作用域化
- **现象**：`get_by_role("combobox", name=...)` 匹配不到（原生 select 无 aria-label）；点击"编辑"命中第一张卡片（种子）。
- **规避**：
  - 对话框内原生 `<select>`：按 `data-testid` 定位（表单组件固定 testid：如 `agent-risk-tier`）。
  - 存在多张卡片/多行时：用 `page.locator(".card", has_text="<唯一标识>").get_by_role("button", name="编辑")` 作用域到目标容器。
  - 交互前先确认"要操作的是哪一行/哪张卡"。
- **教训**：UI 步骤要用"可复现的确定性定位"，不能依赖默认第一个匹配。

## 四、流程 / 工程化层面

### 13. 重跑 = 新环境 → 无脚本重跑必翻车
- 违反任何一条时序（先跑 A 再跑 B、清理、恢复种子），重跑结果不可信。
- **建议**：把"预置 + 清理 + 报告"做成可重复流水线；禁止在状态敏感的场景上手工重试验证。

### 14. 失败信息分层记录
- 保留：junit xml、截图、jtl、失败详情 dump。报告只给"结果"，分析另走 `post-run-analysis`。
- **教训**：一次运行只留一套证据链，供事后归因；不要中途"再看一眼"破坏证据。
