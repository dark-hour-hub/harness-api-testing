# 测试用例编写标准

## 测试用例编写原则

- 每个测试用例只测试一个功能点

- 全面性：测试用例应尽可能覆盖程序的各种正常、异常场景。
- 正确性：测试用例中的输入数据与预期结果必须与实际业务和系统行为一致。
- 符合正常业务惯例：测试数据应符合真实用户业务场景，同时兼顾业务的变化可能性。
- 仿真性：测试用例中使用的模拟数据应真实可信，且避免侵权或不当联想。
- 可操作性：测试用例应详细、无歧义地描述操作步骤及对应的预期结果。
- 可回归性：用例原子化、无执行顺序依赖。


## 测试用例要素

- 核心业务逻辑覆盖率 >= 90%
- UI 测试覆盖主要用户流程

- 测试用例要素包括：测试用例标题、优先级、前置条件、操作步骤、预期结果、用例属性。
- 测试用例标题：格式为系统名称-功能模块-测试功能点，同一集合内不可重复。
- 前置条件：执行前必须满足的环境或数据状态，无则填“无”。
- 操作步骤：有序列表，每步含“操作内容+操作对象”（如：在【金额】输入“100”），粒度适中。
- 预期结果：与步骤对应，描述具体可验证现象或字段值，不包含操作指令。
- 特殊条件：若需特定时间/数据/权限等，单独声明。
- 逻辑一致性：前置条件→步骤→结果，因果关系明确无矛盾。
- 优先级：枚举值 P0（核心路径）、P1（主要功能）、P2（非关键细节）。
- 用例属性，根据用例场景类别及使用场景，可分为正常、异常、回归、冒烟、兼容性、用户体验，一个案例可拥有多个用例属性。


## 测试用例基本设计方法

- 可采用等价类划分法、边界值法、测试大纲法、场景法、错误推断法、随机测试、需求文档转化法等。


## 测试数据的准备与使用

- 测试数据使用 fixture 管理？

- 真实性：数据结构与生产一致，名称、地址、电话等格式符合实际业务规范。
- 准确性：数据值逻辑自洽（如余额与交易历史相符）。
- 多样性-场景：覆盖不同客户类型、交易渠道等真实场景。
- 多样性-值：覆盖边界值、多种格式（日期/电话/账号）及特殊符号。
- 多样性-异常：包含异常数据（非法字符、越界、缺失）验证错误处理。
- 多样性-关键：资金、舆情、业务连续性、批量条目同时包含正常与异常数据。、
- 安全性：敏感信息脱敏处理，访问权限仅限授权人员。
- 量级：批量/性能测试使用生产脱敏数据，量级接近真实环境以暴露慢SQL/死锁。
- 复用性：按场景分类可复用数据，标注时效性，优先复用。





# 接口案例编写标准

## 案例编写要求
- 用例标题:必须包含接口、测试点、预期，避免意义不明。单接口案例格式：{接口方法名}_{测试条件}_{预期结果}；场景案例格式：{场景简述}_{预期业务结果}。
- 用例标签:每条用例必须明确标签属性（如是否回归），不可缺失。
- 案例有效性：同一参数或场景，仅保留代表性案例（有效/无效值各选典型），避免冗余。
- 案例边界：若单用例含多接口，必须是同一业务流程的连续环节（前输出为后输入）；否则一个用例仅测试一个接口。
- 独立性：接口测试案例与手工测试案例分离，接口用例中不得包含手工操作步骤。



## 断言规范

- 使用明确的断言消息
- 断言失败时提供有用的错误信息

- 断言必须分层、完整、精准，禁止缺断言、弱断言、无效断言。
- 断言-协议层：必须断言 HTTP 状态码（如200）或 Dubbo 响应状态。
- 断言-业务层：必须断言业务状态码（如 code:00000, msg:success）。
- 断言-数据层：按需断言具体业务数据（字段存在性、类型、值、数据库一致性）。
- 单接口必须包含协议层、业务层、核心数据层断言。业务场景接口必须逐层断言，并最终校验数据库落地数据。
- 断言禁止项：不允许仅断言 HTTP 状态码、无断言、断言过于简单（如含 null）、断言固定返回的 Key；dubbo 接口不得混用 HTTP 协议。



## 接口用例设计原则

- 正向功能：输入合法数据，验证接口返回预期正确结果。
- 反向功能：输入非法数据，验证接口返回清晰错误码及错误信息，且系统不崩溃。




## 测试命名

- 测试文件：test_{模块名}.py
- 测试函数：test_{功能描述}
- 测试类：Test{模块名}
