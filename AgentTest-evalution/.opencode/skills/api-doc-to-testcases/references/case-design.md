# 用例设计规则

基于 `.opencode/rules/testCase-standards.md` 和 `.opencode/rules/testPoint-interface.md` 的用例设计原则。

---

## 每条接口的用例数量

**每个接口生成 2 条用例**：
- 1 条正向用例（P0）
- 1 条反向用例（P1）

不再按错误表展开多条反向用例，不再生成参数校验用例。

---

## 正向用例（P0）

**构造**：
- 必填字段填合法值
- 使用 `auth.required: true`（认证接口）或 `false`（公开接口）
- 使用默认账号 `account: "admin"`

**断言**（精简）：
- `status_code`：200
- `business_code`：200（或文档指定的成功码）
- `data_exists`：仅 1-2 个关键字段（不过度断言，不需要覆盖全量 data 字段）
- `business_message`：不强制断言
- `data_equals`：不填（尽量少用）

**标签**：`[正常, 回归]`，核心流程接口额外加 `[冒烟]`

---

## 反向用例（P1）

**构造**：
- 按以下优先级选取触发条件：
  1. **业务规则违规**（若文档有「业务规则」表）— 选 1 个典型违规
  2. 接口文档的「错误响应」表 — 选 1 个最有代表性的触发条件
  3. 必填参数缺失、典型业务错误（如用户名已存在）
  4. 参数格式错误、权限不足

**断言**（精简）：
- `status_code`：200 或文档指定的错误 HTTP 状态码
- `business_code`：500（或文档指定的错误码）
- `business_message`：不强制断言
- `data_exists`：不填（错误响应通常 data 为 null）

**标签**：`[异常, 回归]`

---

## 共性错误不随接口重复

以下错误**全项目仅生成 1 条**，不随接口重复：

| 错误类型 | 生成位置 | 说明 |
|---------|---------|------|
| 401 Token 缺失/失效 | 仅在认证模块的某个认证接口生成 | 不随每个模块重复 |
| 403/500 权限不足 | 仅在 1 个代表性接口生成 | 不随每个模块重复 |

---

## 业务规则驱动

若模块文档中包含「业务规则」表，应按以下方式转化为用例：

### 正向用例
- 请求数据应满足所有业务规则（如唯一性约束、范围约束、关联性约束）
- 若业务规则涉及状态流转，正向用例应覆盖合法的状态变更路径

### 反向用例
- 从业务规则表中选取 1 条"最易触发"的规则作为反向条件
- 优先选：数据唯一性冲突、业务状态不合法、关联数据不存在
- 次选：数值范围超限、时间窗口限制
- 操作步骤描述中使用业务规则原文中的术语
- 预期结果描述引用业务规则定义的错误提示

### 多规则场景
- 若一个接口涉及多类业务规则，选择最具代表性（能覆盖最多规则逻辑）的一条生成反向用例

## 断言参照（diff 模式专用）

diff 模式下，输入的接口文档可能已包含每个接口的预期断言。处理规则：

### 文档断言提取
- 查找文档中每个接口的预期响应描述（通常以表格形式给出 status_code、business_code、data 字段）
- 将文档断言值直接填入 YAML `expected` 块

### 断言优先级

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | 文档明确声明的断言 | 直接使用，不做修改 |
| 2 | 文档成功响应示例 | 从示例 JSON 推断字段存在性 |
| 3 | 默认推断规则 | 当前的标准推断逻辑 |

### 文档有断言时的处理
- `status_code`：文档写 200 → YAML 填 200
- `business_code`：文档写 code:0 / code:200 → YAML 填对应值
- `data_exists`：文档列出预期返回字段 → 选取 1-2 个填入
- **禁止**：用 Agent 推断值覆盖文档明确写的值

---

## 优先级分配

| 优先级 | 适用场景 |
|--------|---------|
| P0 | 核心路径：登录、主要 CRUD 正向流程、核心业务流程 |
| P1 | 主要功能：次要查询、状态变更、反向用例、常见错误路径 |
| P2 | 非关键细节：边界值、罕见错误、兼容性（除非明确需要，一般不生成） |

---

## 核心流程判定（加 `冒烟` 标签）

以下接口的正向用例额外加 `[冒烟]` 标签：
- 登录接口（`/auth/login`）
- 各模块的「查询列表」接口（冒烟验证模块可用）
- 核心 CRUD 主接口（如创建用户、创建角色）

---

## 数据安全规则

### 账号保护

`auth_setup.accounts` 中列出的账号**不生成增/删/改用例**。

- 禁止：对 `admin` 账号生成 `DELETE /system/user/{userIds}` 用例
- 禁止：对 `admin` 账号生成 `PUT /system/user/changeStatus` 用例
- 允许：对 `admin` 账号生成 `GET /system/user/list` 查询用例

### params 参数保护

`auth_setup.params` 中的参数对应的资源 **不生成删/改用例**。

### 替代策略

如需测试增删改逻辑：
1. 先用 `POST` 创建一条**新数据**（非账号/认证相关）
2. 对这条新数据执行 `PUT` 修改
3. 对这条新数据执行 `DELETE` 删除

**认证永远使用提供的账号**，不切换到新建账号。

## 标题格式

```
{METHOD} {路径}_{测试条件}_{预期结果}
```

示例：
- `POST /auth/login_正常登录_返回token`
- `GET /system/user/list_查询用户列表_返回分页数据`
- `POST /system/user_用户名为空_返回错误`
- `DELETE /system/user/{id}_删除不存在的用户_返回错误`

---

## ID 格式

```
TC_{MODULE}_{序号}
```

- `MODULE`：从模块文件名提取的大写标识（如 `01-认证模块.md` → `AUTH`）
- 序号：三位数字，从 `001` 开始递增
- 正反用例序号连续（如 TC_AUTH_001 正向、TC_AUTH_002 反向）
