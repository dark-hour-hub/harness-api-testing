# 测试失败分析与经验回写（post-run-analysis）

在每次测试执行（API / UI / Perf）产出报告后，询问用户是否分析本次失败用例；用户要求后，分析根因、甄别"非被测项目的 bug"，输出给用户确认，确认后分层回写经验库，形成持续迭代。

## 职责边界

- 只做**分析 + 经验回写**，不执行测试、不修改用例（除非是测试自身的 bug 修正，需另走对应流程）。
- 分析对象 = **本次执行失败的用例 / 不达标场景**（来自新产出的报告）。
- 产出：① 失败根因清单；② 「非被测项目 bug」→ 经验条目（含归属层级）；③ 回写确认。

## 两级经验库

| 层级 | 位置（以仓库根为锚） | 面向 |
|------|------|------|
| 企业级 | `experience-library/ENTERPRISE-KNOWN-ISSUES.md` | 所有项目执行前必须吸取（工具链/框架/脚本/环境/方法论） |
| 项目级 | `AgentTest-evalution/experience-library/PROJECT-KNOWN-ISSUES.md` | 本项目后续测试避免（被测系统行为事实、ID、配方、基准资源） |

> 仓库 ≠ 项目：经验库位置以「仓库根」为锚做相对解析（禁止写死绝对路径）；若仓库内存在多个测试项目，按 `<仓库根>/experience-library`（企业级）与 `<项目目录>/experience-library`（项目级）约定。

## 工作流程

### 步骤 0：触发与确认（Rule: 先问后析）
只有当本次执行**存在失败/不达标**时进入本流程。向用户提问，例如（三选一即可，用 question 工具）：

> 本次 {api|ui|perf} 测试有 N 个失败/不达标。（另用选项列出）是否分析失败用例？
> - 分析并沉淀经验（推荐）
> - 只分析不沉淀
> - 暂不分析

若用户不要求分析：结束，不输出任何分析内容。

### 步骤 1：采集证据
只读新产出的报告证据，不重跑：
- API：`report/<api-test>/.cache/results_*.xml`（失败测试的 failure text）、失败详情 dump（若有）
- UI：`report/<ui-test>/screenshots/*.png` + junit xml + 失败场景错误堆栈
- Perf：`report/<api-perf>/.cache/result_*.jtl`（错误码/responseMessage 分布）
- 必要时对照被测系统源码 / 响应报文（curl 只读探针）

### 步骤 1.5：定位失败 → 地图修复建议（新增）

当失败原因为定位类（找不到按钮/输入框/元素超时）时，额外执行：

1. 只读获取目标页面当前 DOM（curl 或 playwright probe，禁止重跑用例）
2. 对照失败步骤文案与 `ui-profile/elements.yaml` 现有条目，判断：文案变更？策略失效？缺失条目？
3. 输出「地图修复建议」：`文案 → { type: xxx, value: xxx }`（新策略），与失败分析一并提交用户确认
4. 用户确认后写入 `ui-profile/elements.yaml`，并运行 `python scripts/validate_elements.py` 校验

铁律：AI 只产出建议，**不经确认禁止修改元素地图**（执行层确定性边界）。

### 步骤 2：归因分类
对每个失败用例，归因到以下三类之一：

1. **被测系统 bug**：被测项目代码缺陷（真实产品缺陷）。
2. **非被测项目 bug**（本次要沉淀的目标）：
   - 测试数据/种子/残留问题（唯一约束、脏数据、破坏种子）
   - 测试脚本/用例定义问题（断言错误、错误 body、错误 id、错误文案）
   - 测试工具链/skill/生成器 bug
   - 环境问题（端口、编码、时区、依赖/版本）
3. **无效测试 / 设计缺陷**：用例本身设计不可达、过时、假设错误。

只把第 2 类沉淀为经验（针对其他两类，给出结论即可，不写经验库）。

### 步骤 3：输出待确认清单
按层级分组，每条经验含：
- `现象`（失败表现）
- `根因`（为什么）
- `规避/修复`（怎么做）
- `归属`（项目级 / 企业级 / 两者）

用表格或列表清晰呈现，**结束前必须请用户确认**：
- 每条经验的归属是否正确（可要求调整层级）
- 内容是否准确
- 是否同意回写

### 步骤 4：回写（用户确认后）
- 分别追加到企业级 / 项目级经验库 markdown 的对应分区，并在 `## 维护记录` 表新增一行（日期、来源项目、条目）。
- 回写原则：
  - 企业级只放**跨项目通用**的（框架、工具链、脚本、环境、方法论）。
  - 项目级放**本项目特有**的（被测系统行为、ID、配方、基准资源、本地事实）。
  - 同一坑若两处都该写（如"重跑前清理唯一约束残留"），两边各写一条并互相引用。
- 若用户确认某条应修正现有条目（覆盖/合并），先读现文件再编辑，不重复堆叠。

### 步骤 5：收尾
告知用户已回写条目数与位置；并提示：企业级经验库已被纳入"执行前必读"（runner skill 前置检查），下一次执行会自动对照。

## 铁律

- **禁止未经用户确认直接回写经验库**。
- **禁止分析被测系统 bug 后越权修复被测代码**（结论交回用户）。
- **禁止重跑测试取证**；证据只来自已产出的报告与只读探针。
- **禁止为凑经验而把"被测系统 bug / 无效测试"硬写进经验库**。

## 输出模板（向用户）

```
**失败分析结果**（{api|ui|perf}，N 个失败/不达标）

### A. 非被测项目 bug → 建议沉淀为经验
| # | 现象 | 根因 | 规避/修复 | 归属 |
|---|------|------|-----------|------|
| 1 | ... | ... | ... | 企业级/项目级 |

### B. 其他失败（不写经验库）
- 被测系统 bug：...
- 无效测试/设计缺陷：...

请确认：以上归属与内容是否正确？确认后我将回写（企业级 X 条、项目级 Y 条）。
```

## 与 runner skill 的关系

- `test-runner` / `ui-runner` / `perf-runner` 产出报告后只输出统计与路径，然后询问"是否分析本次失败用例"；本 skill 承接后续分析。
- runner 的"禁止分析"铁律不适用于本 skill（本 skill 是独立的分析职责方）。
