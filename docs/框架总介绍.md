## 1. 框架概述

AgentTest-evalution 是一套**由 AI 驱动的自动化测试框架**，面向"被测系统 → 测试产出物"的全自动流水线，覆盖三类测试：

| 测试线 | 命令 | 技术栈 | 最终产物 |
|--------|------|--------|---------|
| 接口功能测试（API） | `/test` | CodeGraph + pytest + HTML 报告 | YAML 用例 → pytest 脚本 → 聚合报告 |
| 接口性能测试（Perf） | `/perf-test` | JMeter 5.x | 性能场景 YAML → .jmx → 压测报告 |
| 界面测试（UI） | `/ui-test` | pytest-bdd + Playwright + Element Plus 定位体系 | Gherkin 场景 → 脚本 → 截图报告 |

**核心特征**：

- **AI 介入 + 人工闸门**：分析、文档、用例生成由 AI（skill 驱动）完成；写入任何配置/用例前必须经人工确认。
- **产物即证据**：每个阶段有固定产物文件，缺失即流程中止。
- **执行与修复分离**：runner skill 只执行、禁止分析/修复/重跑；失败分析由 post-run-analysis 单独承接。
- **配置驱动，零硬编码**：被测项目地址、账号、工具路径全部来自 `config.yaml`；skill 内禁止写死绝对路径。
- **经验沉淀闭环**：每次失败经分析归类后回写两级经验库（企业级/项目级），下次执行前自动对照。

## 2. 设计思想与核心机制

### 2.1 产物链（Pipeline）思想

每条测试线都是一条**单向产物链**：前一步的产物是后一步的输入。

```
源码 ──analyze──▶ apis.json ──discover──▶ _manifest.yaml ──entities/module──▶ 接口文档
     ──to-testcases──▶ YAML 用例 ──yaml-to-pytest──▶ pytest 脚本 ──test-runner──▶ HTML 报告
```

产物即证据：`test.md` / `perf-test.md` / `ui-test.md` 中每个阶段标注了**产物路径**，AI 必须在阶段结束后验证产物存在，否则中止流程。

### 2.2 人工确认闸门

以下操作**未经用户确认禁止写入**（skill 铁律）：

- 写入 `ui-profile/elements.yaml`、`ui-profile/business.yaml`（ui-requirements-analyze / ui-element-map / post-run-analysis 的"地图修复建议"）
- 写入 `00-requirements/db-asserts.yaml`
- 回写经验库（post-run-analysis）

### 2.3 执行与修复分离（红牌铁律）

`test-runner` / `ui-runner` / `perf-runner` 执行结束后**只允许**输出统计摘要和报告路径；禁止分析根因、修改用例、重新执行。失败分析统一由 `post-run-analysis` 在用户同意后进行。这一设计保证"一次运行 = 一份可信证据链"。

### 2.4 两级经验库

| 层级 | 文件 | 内容 | 维护者 |
|------|------|------|--------|
| 企业级 | `experience-library/ENTERPRISE-KNOWN-ISSUES.md` | 跨项目通用坑：工具链/脚本/框架/环境/方法论 | post-run-analysis（用户确认后回写） |
| 项目级 | `AgentTest-evalution/experience-library/PROJECT-KNOWN-ISSUES.md` | 本项目特有事实：被测系统行为/ID/配方/基准资源 | 同上 |

runner skill 执行前的"前置检查"会对照企业级经验库。位置以**仓库根为锚**相对解析，禁止写死绝对路径。

### 2.5 双模式：baseline 与 diff

接口与 UI 链路均支持 `--mode baseline|diff`：

- **baseline（全量）**：`tests/baseline/_workflow → generated → report`
- **diff（增量）**：`tests/diff/_workflow → generated → report`；由 `api-doc-diff` 基于代码变更文档/git diff 生成**仅变更部分**的文档与用例，未变更的模块不生成。

## 4. 命令（Command）全流程

命令位于 `.opencode/commands/`，是**全流程编排入口**，内部通过调用 skill 与脚本串联阶段。每个阶段标注了"AI 介入/自动"、输入、产物与"产物即证据"校验点。

### 4.1 `/test` — 接口测试全流程（10 阶段）

| 阶段 | 名称 | 方式 | 调用 | 产物 |
|------|------|------|------|------|
| 01 | 配置检查 | 自动 | `scripts/check_env_deps.py` | `_workflow/01-config/output.json` |
| 02 | 分析规划 | AI | analyze-source | `_workflow/02-analysis-plan/generation-plan.md`、`apis.json` |
| 03 | 框架分析 | AI | framework-analyzer | `_workflow/02-analysis-plan/framework-analysis.md`（+`auth-analysis.md`） |
| 04 | 接口发现 | AI | api-doc-discover | `_workflow/03-api-docs/_manifest.yaml`、`API接口文档.md` |
| 05 | 实体文档 | AI | api-doc-entities | `_workflow/03-api-docs/entities/*.md`、`_index.yaml` |
| 06 | 模块文档 | AI | api-doc-module | `_workflow/03-api-docs/modules/*.md` |
| 07 | 文档组装 | AI | api-doc-assemble | 更新 `API接口文档.md`（回填概览）、`_manifest.yaml` |
| 08 | 用例生成 | AI | api-doc-to-testcases | `_workflow/04-testcases/{模块}.yaml` |
| 09 | 脚本生成 | 自动 | yaml-to-pytest（`generate_pytest.py`） | `generated/api-test/test_{module}.py`、`conftest.py` |
| 10 | 用例执行 | 自动 | test-runner（`run_tests.py`） | `report/api-test/report_*.html`（**只执行不修复**） |

### 4.2 `/perf-test` — 性能测试全流程（3 阶段，与 test 平行独立）

| 阶段 | 名称 | 方式 | 调用 | 产物 |
|------|------|------|------|------|
| 01 | 性能场景生成 | AI | api-doc-to-perf | `_workflow/05-perf-scenarios/{模块}.yaml` |
| 02 | 压测脚本生成 | 自动 | yaml-to-jmx（`generate_jmx.py`） | `generated/api-perf/{scenario_id}.jmx`、`_scenarios.json` |
| 03 | 压测执行与报告 | 自动 | perf-runner（`run_perf.py`） | `report/api-perf/report_*.html`（只执行不修复） |

复用 test 链路的 03-api-docs 与 02-analysis-plan 产物作为输入；不复用其 skill 与产物。

### 4.3 `/ui-test` — UI 测试全流程（5 阶段）

| 阶段 | 名称 | 方式 | 调用 | 产物 |
|------|------|------|------|------|
| 01 | 需求整理 | AI | （用户提供/复用） | `_workflow/00-requirements/ui-requirements.md` |
| 02 | 环境检查 | 自动 | `scripts/check_ui_env.py` | `_workflow/01-config/ui-env.json`（`ready=true` 才继续） |
| 03 | 场景设计 | AI | ui-scenario-design | `_workflow/04-ui-scenarios/*.feature`、`_manifest.yaml` |
| 04 | 脚本生成 | 自动 | feature-to-playwright（`generate_playwright.py`） | `generated/ui-test/test_{module}.py`、`conftest.py` |

## 6. 技能（Skills）详解

位于 `.opencode/skills/{skill}/`，标准结构：`SKILL.md`（必含）+ 可选 `references/`（规则）、`scripts/`（自动化脚本）、`template/`（输出模板）。按三条链路分组。

### 6.1 API 文档链路（阶段 02-07）

#### analyze-source — 源码分析（test 阶段 02）
- **作用**：初始化 CodeGraph 索引（`codegraph init -i`），用 CodeGraph 工具族（search/context/trace/impact/route）全量枚举路由、提取 DTO/VO 字段、追踪错误路径（Controller→Service→全局异常处理器）、技术栈检测、认证粗判（`requires_auth`）。
- **输入**：`config.yaml`（源码路径）、被测项目源码。
- **输出**：`tests/baseline/specs/{module}/*-analysis.md`、`*-spec.yaml`、`_workflow/02-analysis-plan/apis.json`、`generation-plan.md`。
- **配套**：`template/analysis-reference.md`（类型映射参考）、`template/generation-plan-template.md`（计划模板）、`template/output-formats.md`（输出格式）。
- **衔接**：apis.json → api-doc-discover 复用；generation-plan → 阶段产物证据。
- **关键约束**：路径拼接禁止凭类名推断；HTTP 方法禁止凭方法名推断；全量枚举禁止挑"代表性"API；错误路径必须三层追踪。

#### framework-analyzer — 框架与认证分析（test 阶段 03）
- **作用**：解析 `pom.xml` 识别技术栈；深度分析认证机制（Shiro/Spring Security/Sa-Token/自定义 Filter/拦截器），提取必填请求头、Token 来源、拦截/白名单路径、登录接口、关键配置（脱敏）。
- **输入**：`config.yaml`、被测项目源码。
- **输出**：`_workflow/02-analysis-plan/framework-analysis.md` + `auth-analysis.md`（无认证也必须输出，标注 `type: none`）。
- **配套**：`references/pom-analysis.md`（依赖分类矩阵）、`references/auth-detection.md`（认证特征表与搜索模式）、`references/output-format.md`（报告模板）。
- **衔接**：auth-analysis → api-doc-discover（白名单/请求头）、api-doc-to-testcases（auth_setup）、api-doc-to-perf（token JSONPath）。

#### api-doc-discover — 接口发现与分组（test 阶段 04）
- **作用**：全量路由发现（优先复用 apis.json，抽查校验）、排除非业务路由、按 URL 前缀分组模块、评估拆分计划、收集 DTO/VO 清单、确认响应包装类（R/ApiResponse 等，**以源码为准**）、写主文档骨架。
- **输入**：`config.yaml`、`auth-analysis.md`、`framework-analysis.md`、`apis.json`。
- **输出**：`_workflow/03-api-docs/_manifest.yaml`（下游契约）、`API接口文档.md`（骨架）。
- **配套**：`references/_manifest-format.md`（manifest 格式定义）。
- **衔接**：manifest → api-doc-entities / api-doc-module / api-doc-to-testcases / api-doc-to-perf。

#### api-doc-entities — 实体类文档（test 阶段 05）
- **作用**：按模块**并行派发 Agent**，用 CodeGraph 批量读 DTO/VO 源码，按 JSON 键名优先级链（@JsonProperty > @JsonNaming > 全局配置 > 默认）与必填判定生成实体文档；汇总 `_index.yaml`。
- **输入**：`config.yaml`、`_manifest.yaml`（all_dtos/all_vos）、`references/实体类文档模板.md`。
- **输出**：`_workflow/03-api-docs/entities/{ClassName}.md`、`entities/_index.yaml`。
- **配套**：`references/field-resolution.md`（JSON 键名优先级/特殊类型/类型映射）。
- **衔接**：实体文档 → api-doc-module（实体引用）、api-doc-to-testcases（字段/校验规则）。
- **关键约束**：禁止逐条 codegraph_node；必须追踪父类字段；注解转义必须记录。

#### api-doc-module — 模块接口文档（test 阶段 06）
- **作用**：按 manifest 的 split_plan 并行派发 Agent，逐接口生成"属性表 → 请求 → 响应（成功/错误）→ 业务规则"完整文档；错误消息做 **i18n 解析**；校验规则必须以注解原文为准。
- **输入**：`config.yaml`、`_manifest.yaml`、`API接口文档.md`、`entities/`、`references/模块文档模板.md`、`references/i18n-resolution.md`。
- **输出**：`_workflow/03-api-docs/modules/{序号}-{模块}.md`（含 part 拆分）。
- **衔接**：模块文档 → api-doc-assemble（回填）、api-doc-to-testcases / api-doc-to-perf（用例/场景生成）。

#### api-doc-assemble — 文档汇总校验（test 阶段 07）
- **作用**：统计模块文档实际接口数，回填主文档"模块概览"表、汇总已知问题、校验格式（无摘要表/无内联字段/四级标题完整/无未替换占位符）、回写 `interface_count`。
- **输入**：`API接口文档.md`、`_manifest.yaml`、`modules/`、`entities/_index.yaml`。
- **输出**：更新 `API接口文档.md`、`_manifest.yaml`。
- **关键约束**：只读校验模块文档，禁止修改/重读源码。

#### api-doc-diff — 增量 API 文档（diff 模式）
- **作用**：基于代码变更文档（`tests/diff/doc/*.md`）或 git diff + CodeGraph，判定 added/modified/deleted，仅生成变更部分的实体/模块文档；**为变更接口生成"断言"节**（协议/业务/数据三层断言表，供下游直接映射 YAML expected）。
- **输入**：`config.yaml`、`tests/diff/doc/`、基线 `tests/baseline/_workflow/03-api-docs/`。
- **输出**：`tests/diff/_workflow/01-diff-api-doc/`（仅受影响模块/实体）。
- **配套**：`references/diff-rules.md`（变更判定规则）。
- **关键约束**：禁止修改基线 03-api-docs；未变更的模块不生成。

### 6.2 接口用例与执行链路（阶段 08-10）

#### api-doc-to-testcases — 接口用例生成（test 阶段 08，双模式）
- **作用**：从模块/实体/认证文档构建全局配置（headers_config、auth_setup、global_variables），并行派发模块 Agent 生成 YAML 用例；diff 模式先提取登录用例、优先照搬文档内断言。
- **输入**：`API接口文档.md`、`auth-analysis.md`、`_manifest.yaml`、`modules/*.md`、`entities/*.md`、rules、`references/testcase-example.yaml`。
- **输出**：`_workflow/04-testcases/{模块}.yaml`（baseline）/ `_workflow/02-diff-testcases/`（diff）。
- **配套**：`references/yaml-schema.md`（字段规范）、`case-design.md`（用例设计）、`doc-mapping.md`（文档→YAML 映射）、`variable-reference.md`（${} 引用规则）、`generation-rules.md`（生成约束）、`auth-config.md`（认证配置构建）、`template/module-agent-prompt.md`（Agent 提示词）、`scripts/validate_yaml.py`（校验，失败派修复 Agent 最多 2 轮）。
- **关键约束**：`login_endpoint` 纯路径；body/断言用 JSON 键名；禁止对 auth_setup.accounts 账号生成增删改用例。

#### yaml-to-pytest — YAML → pytest 脚本（test 阶段 09）
- **作用**：数据驱动生成 `test_{module}.py`（每用例一方法）+ `conftest.py`（ModuleContext 上下文、变量递归解析、JSONPath 提取、请求头构建、session 级自动登录、request_helper 断言封装）。
- **输入**：`_workflow/04-testcases/*.yaml`（baseline）/ `02-diff-testcases/`（diff）、yaml-schema.md、variable-reference.md。
- **输出**：`generated/api-test/test_{module}.py`、`conftest.py`。
- **配套**：`scripts/generate_pytest.py`（`--mode`/`--yaml-dir`/`--output-dir`）、`template/conftest.py`。
- **关键约束**：脚本不硬编码测试数据；`multipart/form-data` 用例自动 skip。

#### test-runner — API 执行与报告（test 阶段 10）
- **作用**：逐文件独立 pytest 进程执行（Token/进程/模块隔离），合并 JUnit XML 生成聚合 HTML 报告。
- **输入**：`generated/api-test/`。
- **输出**：`report/api-test/report_<timestamp>.html` + `latest.html` + `.cache/results_*.xml`。
- **配套**：`scripts/run_tests.py`、`template/report_template.html`。
- **铁律**：只执行不修复（见 2.3）；失败时询问是否调用 post-run-analysis。

### 6.3 性能链路

#### api-doc-to-perf — 性能场景生成（perf-test 阶段 01）
- **作用**：从接口文档构建全局配置（auth_headers 用 JMeter `${token}`），每模块选 3~5 个核心接口，按 P0/P1/P2 配并发档位（100/60s、50/60s、20/30s），生成含 load/thresholds 的场景 YAML。
- **输入**：`API接口文档.md`、`auth-analysis.md`、`_manifest.yaml`、`modules/*.md`、`entities/*.md`。
- **输出**：`_workflow/05-perf-scenarios/{模块}.yaml`。
- **配套**：`references/perf-schema.md`（字段契约，与 yaml-to-jmx 对齐）、`template/perf-module-agent-prompt.md`、`scripts/validate_perf.py`。
- **关键约束**：thresholds 非空；load 必含 users/duration；写场景唯一编码用 `${__RandomString(12,A-Z0-9)}`（企业经验库第 5 条）。

#### yaml-to-jmx — 场景 YAML → JMeter 脚本（perf-test 阶段 02）
- **作用**：每场景生成独立 `.jmx`（单 ThreadGroup）；`auth.required: true` 时自动生成 OnceOnlyController + 登录 Sampler + JSON Extractor（token_jsonpath → `${token}`）；POST/PUT/PATCH 用 Raw Post Body。
- **输入**：`_workflow/05-perf-scenarios/*.yaml`、`template/jmx_fragments.py`。
- **输出**：`generated/api-perf/{scenario_id}.jmx` + `_scenarios.json`（id/thresholds/load 元信息）。
- **配套**：`scripts/generate_jmx.py`（生成后 XML well-formed 校验）。
- **关键约束**：sampler testname = 场景 id（大写，.jtl 统计依据）；禁止修改 jmx_fragments.py 的已对齐结构。

#### perf-runner — 压测执行与报告（perf-test 阶段 03）
- **作用**：从 `config.yaml tools.jmeter` 定位 jmeter，逐场景串行独立进程执行，解析 .jtl（排除 login 样本）统计 avg/p50/p90/p95/p99/error_rate/rps，与 thresholds 比对标记达标/不达标，生成报告。
- **输入**：`generated/api-perf/`。
- **输出**：`report/api-perf/report_<timestamp>.html` + `latest.html` + `.cache/result_<id>.jtl`。
- **配套**：`scripts/run_perf.py`、`template/perf_report_template.html`。
- **铁律**：只执行不修复；不达标时询问是否分析。

### 6.4 UI 链路

#### ui-requirements-analyze — 需求 → 项目绑定四件套
- **作用**：解析 5 节模板需求文档（模块与版本/业务流程/数据变更映射/字段明细/数据约束），对照前端源码与后端 schema.sql，产出**四件套草稿**：`ui-profile/elements.yaml`、`ui-profile/business.yaml`、`00-requirements/db-asserts.yaml`、api_sync_rules。输出"业务命名 vs 物理命名"差异表，人工确认后入库。
- **输入**：`00-requirements/ui-requirements.md`（5 节模板）、前端源码、后端 `db/schema.sql`、API 文档。
- **输出**：四件套（草稿 → 确认 → 入库）。
- **配套**：`references/db-asserts-example.yaml`（DB 断言映射格式示例）。
- **职责边界**：一次性绑定；elements.yaml 的增量维护由 ui-element-map 负责。
- **关键约束**：禁止凭空编造定位文案/表名/字段名；未经确认禁止写入。

#### ui-element-map — 元素地图增量维护
- **作用**：扫描前端 `.vue` 源码提取按钮文本/placeholder/data-testid/下拉文案，与场景文本（`_element-candidates.yaml` + `.feature`）对齐，生成 `elements.yaml.draft` → `validate_elements.py` 校验 → 人工确认后入库。
- **输入**：`config.yaml`（前端路径/URL）、现有 `ui-profile/elements.yaml`、`04-ui-scenarios/`。
- **输出**：更新 `ui-profile/elements.yaml`。
- **关键约束**：定位文案必须来自源码；只增改不删已确认条目；校验不通过禁止入库。

#### ui-scenario-design — 业务需求 → Gherkin 场景（ui-test 阶段 03）
- **作用**：以需求文档 + 元素地图为输入，读前端源码提取定位文案，用**通用步骤 DSL** 编写 `.feature` 场景；产出 `_manifest.yaml` 清单与 `_element-candidates.yaml` 候选清单（供 ui-element-map 补入）。
- **输入**：`00-requirements/ui-requirements.md`、`ui-profile/elements.yaml`、`00-requirements/db-asserts.yaml`（引用其 id）、前端源码/地址/账号。
- **输出**：`04-ui-scenarios/*.feature`、`_manifest.yaml`、`_element-candidates.yaml`（可选）。
- **配套**：`references/gherkin-guide.md`（步骤 DSL 与编写规则）、`references/requirement-template.md`（5 节需求模板）。
- **关键约束**：场景必须用通用 DSL；`And` 继承关键字陷阱（Given 行后必须显式 When）；scenario 名用英文。

#### feature-to-playwright — Gherkin → pytest-bdd 脚本（ui-test 阶段 04）
- **作用**：每 feature 生成 `test_{module}.py`（scenarios() 绑定）+ 复制通用 `conftest.py`（步骤库 + 自动截图 + DB 断言步骤）；从 `00-requirements/db-asserts.yaml` 编译 `db_asserts.py`（生成期静态校验表/列/变量）。
- **输入**：`04-ui-scenarios/*.feature`、`00-requirements/db-asserts.yaml`、`ui-profile/`（运行期决议：环境变量 > ui-profile/ > ui-profile-template/）。
- **输出**：`generated/ui-test/test_{module}.py`、`conftest.py`、`db_asserts.py`。
- **配套**：`scripts/generate_playwright.py`、`template/conftest.py`。
- **关键约束**：生成后必须 `pytest --collect-only` 自检步骤错配；禁止修改 conftest.py（模板产物）。

#### ui-runner — UI 执行与报告（ui-test 阶段 05）
- **作用**：chromium 无头逐 feature 独立进程执行，成功/失败自动截图，生成含截图与步骤明细的 HTML 报告；执行前比对前端指纹（`ui_fingerprint.py`），变更则提示检查元素地图。
- **输入**：`generated/ui-test/`。
- **输出**：`report/ui-test/report_*.html` + `latest.html` + `screenshots/*.png` + `.cache/results_*.xml`。
- **配套**：`scripts/run_ui.py`、`template/ui_report_template.html`。
- **铁律**：只执行不修复；失败时询问是否分析。

### 6.5 公共分析链路

#### post-run-analysis — 失败分析与经验回写
- **作用**：报告产出后（用户同意）分析失败用例：采集证据（.xml/.jtl/截图）→ 定位类失败产出"地图修复建议"（确认后写入 elements.yaml）→ 归因三类（被测系统 bug / 非被测项目 bug / 无效测试）→ 仅将"非被测项目 bug"沉淀为经验 → 用户确认后回写两级经验库。
- **输入**：`report/*/.cache/*`、截图、jtl；必要时只读探针。
- **输出**：失败分析清单；确认后回写经验库。
- **关键约束**：禁止未经确认回写；禁止重跑取证；禁止越权修复被测代码。

### 7.1 `_manifest.yaml`（api-doc-discover 产出，下游契约）

| 段 | 内容 |

### 7.2 YAML 用例契约（api-doc-to-testcases → yaml-to-pytest）

- 顶层：`module` / `module_name` / `base_url` / `global_variables` / `headers_config` / `auth_setup` / `testcases`。
- `auth_setup.type`：`bearer_token` / `basic` / `apikey` / `oauth2` / `none`。
- 用例：`id`（TC_{MODULE}_{序号}）/ `title` / `priority` / `tags` / `method` / `path` / `auth` / `request` / `extracts` / `expected` / `depends_on`。
- `expected`：`status_code`（协议层）+ `business_code`/`business_message`（业务层）+ `data_exists`/`data_equals`（数据层）——对应 rules 三层断言。
- 变量：`${auth.token}`（跳过 extracts 层级）、`${auth.params.x}`、`${global_variables.x}`、`${TC_XXX.extracts.x}`（跨用例）。

### 7.3 性能场景契约（api-doc-to-perf → yaml-to-jmx）

- 顶层与用例同构；`scenarios[]` 含 `load`（users/ramp_up/duration/loops）与 `thresholds`（avg/p50/p90/p95/p99/error_rate/min_rps，至少一项）。
- `auth_setup`：`login_endpoint`（纯路径）/ `login_method` / `login_body` / `token_jsonpath` / `token_default`。
- 认证头 Token 用 JMeter 变量 `${token}`（区别于接口线的 `${auth.token}`）。

### 7.4 db-asserts.yaml（UI 线 DB 断言契约）

- 唯一产出方：ui-requirements-analyze（`00-requirements/db-asserts.yaml`）。
- 条目：`id`（{模块}_{操作}_{序号}）/ `ui_action` / `table` / `expect_records` / `where` / `assert_fields` / `sync` / `schema_ref`。
- 场景引用：`且数据已保存到 "<id>"`；生成期校验 id/表/列/变量存在性，运行期查库断言。

### 7.5 ui-profile 契约

- `elements.yaml`：`key（文案即 key）→ strategies[]`（`data-testid > label > placeholder > role > text > css`，按序尝试命中即止）。
- `business.yaml`：`busy_indicators` / `timeouts` / `protected_seeds`（fnmatch 种子保护）/ `api_sync_rules`（按钮→等待的后端请求）/ `retry` / `db`（DB 断言连接）。
- 加载决议：`环境变量 UI_PROFILE_DIR > 项目 ui-profile/ > ui-profile-template/`（lib/ui_profile.py:46）。

## 9. 二次开发指南

### 9.1 新增/修改 skill 的规范

1. **目录结构**：`.opencode/skills/{skill-name}/SKILL.md`（必填）+ `references/`（规则/格式）/ `scripts/`（自动化）/ `template/`（模板）。
2. **SKILL.md frontmatter**：`name`（小写连字符）、`description`（含触发词 + 作用 + 触发方式），风格与现有 skill 一致。
3. **内容必含**：
   - 参数与路径决议表（如 `mode` 的 baseline/diff 双模式）；
   - 输入/输出（固定路径，**相对仓库根**，禁止写死绝对路径）；
   - 人工确认闸门（若涉及写配置/用例/经验库）；
   - 铁律（禁止项）；
   - 产物即证据校验点（若被命令编排）。
4. **路径约定**：所有产物路径写相对路径；经验库/runner 前置检查一律用 `experience-library/...`（仓库根为锚）。
5. **跨 skill 协作**：明确上下游（本 skill 消费谁、谁消费本 skill），重复职责（如两份 skill 产出同一文件）必须避免或显式声明"唯一产出方"。
6. **执行脚本**：统一用 `Path(__file__).resolve().parent.parent` 定位 skill 目录，`--mode` 参数决议路径，输出编码 `utf-8, errors="replace"`（Windows 兼容）。

### 9.2 新增命令的规范

- 结构：阶段编号（01-10）→ 名称 → 方式（AI/自动）→ 调用（skill 或 `python scripts/...`）→ 输入 → **产物路径** → "产物即证据"校验点。
- 遵守 rules（testCase-standards / testPoint-interface）；执行阶段必须标注"只执行不修复"铁律并挂钩 post-run-analysis。

### 9.3 修改既有文件的注意

- 生成器脚本（yaml-to-pytest / yaml-to-jmx / feature-to-playwright 的 scripts + template）是**模板产物**：conftest.py 等被复制到 generated/ 的模板改动后，需重新生成才能生效。
- `jmx_fragments.py` 的 JMeter 元素结构已对齐，改动前确认下游解析逻辑。
- 修改规则/参考文件后，同步检查引用它的 skill 与命令。
- 框架结构变更后，同步更新本文档。
