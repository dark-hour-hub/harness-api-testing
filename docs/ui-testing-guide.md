# UI 测试思想详解：智能体评测平台测试链路的完整解读

> 适用对象：测试工程师、业务人员、开发人员（无需自动化测试背景）
> 覆盖范围：AgentTest-evalution（AIHarness-wu）的 UI 测试链路
> 配套设计文档：`docs/superpowers/specs/2026-08-24-ui-testing-revamp-design.md`、`docs/superpowers/specs/2026-08-25-ui-testing-db-assert-design.md`

---

## 一、这份文档讲什么

这套 UI 测试体系解决三个根本问题：

| 问题 | 答案 |
|------|------|
| 测试用例从哪来？ | 业务需求驱动：业务写需求 → AI 翻译成 Gherkin 场景 |
| 程序怎么在页面上找到元素？ | 元素地图（预写好的"找元素攻略"） |
| 测试怎么保证"真的成功了"？ | 三层断言：UI 提示 → API 返回 → 数据库落库 |

全文围绕"元素地图"展开，因为它是这套体系最核心、也最容易被误解的部分。

---

## 二、核心思想（先记住这 4 条）

1. **业务需求驱动，不关心代码实现**：只关心"用户在页面上做什么、看到什么"
2. **执行层确定性**：测试运行时是固定代码，AI 只做"设计/分析"，绝不在运行时猜
3. **产物即证据**：每个环节必须产出文件，没有产物就中止，防止流程空转
4. **防假成功**：UI 提示出现 ≠ 数据真的落库，要用 API/DB 层层验证

## 三、全流程流水线

```
01 需求整理 → 02 环境检查 → 03 场景设计 → 04 脚本生成 → 05 执行与报告 → (06 失败分析)
  (AI 介入)     (自动)       (AI 介入)     (自动)       (自动)           (AI 介入)
```

| 阶段 | 做什么 | 产物（缺失即中止） |
|------|--------|-------------------|
| 01 需求整理 | 业务按模板写需求文档 | `00-requirements/ui-requirements.md` |
| 02 环境检查 | 检查 Python 依赖/浏览器/前端地址 | `01-config/ui-env.json`（`ready=true`） |
| 03 场景设计 | AI 读需求+前端源码，产出 Gherkin 场景 | `04-ui-scenarios/*.feature` + `_manifest.yaml` |
| 04 脚本生成 | 生成器把场景编译成 pytest 脚本 | `generated/ui-test/test_*.py` + `conftest.py` |
| 05 执行与报告 | chromium 无头跑测试，自动截图 | `report/ui-test/report_*.html` |
| 06 失败分析 | 归因失败，沉淀经验库（仅在有失败时） | 经验库条目（需人工确认） |

**流程纪律**：05 阶段**只执行不修复**——跑完无论结果如何，禁止当场分析失败、禁止改用例重跑。分析交给 06 单独进行。

## 四、场景 DSL：业务语言怎么写

场景用"通用步骤"写，AI 从业务需求翻译。全部步骤：

| 类型 | 步骤 | 例子 |
|------|------|------|
| 前置 | `打开首页` | 打开前端 |
| 前置 | `以账号 "x" 密码 "y" 登录` | UI 登录 |
| 操作 | `点击菜单/按钮/链接 "文案"` | `点击按钮 "保存"` |
| 操作 | `在 "字段" 输入框中输入 "值"` | `在 "请输入书名" 输入框中输入 "测试图书"` |
| 操作 | `选择下拉框 "名称" 的选项 "文本"` | 下拉选择 |
| 操作 | `等待 N 秒` | 固定等待 |
| 操作 | `令 $变量 = "值"` | 声明场景变量（值可含 `${ts}` 动态值） |
| 断言 | `应看到提示 "文案"` | 页面提示消息 |
| 断言 | `页面应包含 / 表格应包含 "文案"` | 可见文本 |
| 断言 | `且数据已保存到 "映射ID"` | **DB 落库断言**（防假成功） |

**场景变量示例**：

```gherkin
And 令 $code = "AGT_UI_${ts}"          # 声明变量，${ts} 是时间戳动态值
And 在 "智能体编码" 输入框中输入 "$code"  # 引用变量
And 点击按钮 "保存"
Then 且数据已保存到 "AGENT_CREATE_001"   # DB 断言引用同一个变量
```

变量保证"创建时用的值"和"断言时查的值"完全一致——否则断言查不到。

## 五、元素地图（核心中的核心）

### 5.1 问题：程序怎么"看见"页面？

人点按钮靠眼睛。程序（Playwright）是"瞎子"，它需要靠**特征**辨认元素。特征就是元素的属性：占位符文字、按钮文字、标签、开发预留的 testid……

**如果靠猜**：每次运行都拿文案去页面"碰运气"地搜——前端改一个字的文案，所有测试全挂，而且你不知道它靠什么找到的。

**元素地图方案**：把"每个元素怎么找"**预先写成配置文件**，测试运行时按配置找。

### 5.2 地图长什么样

文件：`ui-profile/elements.yaml`

```yaml
elements:
  智能体编码:                          # key = 场景步骤里用的业务文案（文案即 key）
    strategies:                       # 策略链 = 按顺序尝试的查找方案
      - { type: placeholder, value: "例如：BANK_AGENT" }   # 方案1：找占位符文字
  风险等级:
    strategies:
      - { type: data-testid, value: agent-risk-tier }      # 方案1：找 testid（最稳）
      - { type: role, role: combobox, name: "风险等级" }   # 方案2：找角色+名称
  保存:
    strategies:
      - { type: role, role: button, name: "保存" }          # 方案1：找按钮
      - { type: text, value: "保存" }                       # 方案2：找纯文本
```

### 5.3 策略链机制：按序尝试，命中即止

运行时执行逻辑（`resolve_element`）：

```
场景步骤: 在 "风险等级" 下拉框选择
        ↓
查地图: elements["风险等级"] 存在
        ↓
方案1: 找 data-testid="agent-risk-tier"
   ├─ 找到 → 用它，记录"策略第 1 级" ✓
   └─ 没找到 → 方案2
方案2: 找 role=combobox 名字="风险等级"
   ├─ 找到 → 用它，记录"策略第 2 级" ✓
   └─ 没找到 → 判失败（红）
```

**策略顺序的设计原则：越可靠越靠前**。`data-testid` 是开发预留的稳定标记（文案改了它还在），所以排第一；`placeholder`/`role` 次之。前端改版时，即使方案1失效，方案2/3 能兜住。

### 5.4 地图是怎么创建的（重点）

创建链路：**前端源码 → AI 提取 → 人工确认 → 入库**。绝不允许 AI 凭空编造文案。

```
步骤1  读前端源码（config.yaml 里配置的前端工程路径）
        ↓
步骤2  对每个交互元素提取真实特征：
       ├─ 输入框 → placeholder 文案（如 <el-input placeholder="例如：BANK_AGENT" />）
       ├─ 按钮/菜单 → 可见文本（如 <el-button>保存</el-button>）
       ├─ 下拉框 → data-testid 或 aria 属性（如 data-testid="agent-risk-tier"）
       └─ 提示 → ElMessage 里的字符串（如 ElMessage.success('智能体已新增')）
        ↓
步骤3  AI 产出草稿（elements.yaml 候选 + _element-candidates.yaml 候选清单）
        ↓
步骤4  测试工程师确认/修正 → 入库 ui-profile/elements.yaml
```

**三条铁律**：
1. **文案即 key**：场景步骤的文案必须与地图 key 完全一致，才能命中地图
2. **来源必须真实**：定位文案必须来自前端源码，禁止凭空猜测
3. **前端变了只改地图**：改文案/加 testid 都只动 elements.yaml 一处，场景和测试脚本不用动

### 5.5 命中报告怎么读（体检表）

每次测试跑完，报告末尾生成「元素地图命中报告」：

```
元素                   命中方式    策略级别
$.answer              地图命中    策略第 1 级
例如：CUSTOMER_SERVICE 地图命中    策略第 1 级
风险等级               地图命中    策略第 1 级
```

| 列 | 含义 | 看到什么代表什么 |
|----|------|-----------------|
| 元素 | 场景用到的业务文案（= 地图 key） | 本次运行交互过的所有元素 |
| 命中方式 | 地图命中=走策略链找的；回退=地图里没有，文案直搜碰运气 | **回退 = 红色预警，该补地图** |
| 策略级别 | 策略链里第几个方案成功 | 第 1 级=首选方案；第 2+ 级=首选失效自动降级（黄） |

**三种健康状态**：

| 状态 | 颜色 | 含义 | 该做什么 |
|------|------|------|---------|
| 全绿（第 1 级） | 绿 | 所有元素按首选方案稳定定位 | 什么都不用做 |
| 降级（第 2+ 级） | 黄 | 前端结构变了，首选方案失效，兜底方案接住了 | 检查前端改动，更新地图首选策略 |
| 回退 | 红 | 元素没地图保障，文案一改就挂 | 补地图条目 |

一句话：**命中报告 = 元素定位健康度体检表**。绿=受控稳定，黄=降级预警，红=裸奔脆弱。

## 六、三层断言体系（防假成功）

### 6.1 为什么 UI 提示不够

`应看到提示 "智能体已新增"` 只能证明"前端显示了这个 toast"，不能证明"后端真的写了数据库"。前端乐观更新、后端 bug（返回成功但没写库）都会造成"提示有了、数据没落"。

### 6.2 三层验证，逐层加强

| 层 | 验证什么 | 强度 | 例子 |
|----|---------|------|------|
| UI 提示 | 用户看到了什么 | 弱 | `应看到提示 "智能体已新增"` |
| API 返回 | 系统声称做了什么 | 中 | 点保存时自动等 `POST/PUT /api/agents` 返回 200 |
| DB 落库 | 数据实际发生了什么 | 强 | `且数据已保存到 "AGENT_CREATE_001"`（真查数据库） |

### 6.3 API 返回校验怎么工作

`ui-profile/business.yaml` 里配置"哪个操作对应哪个接口"：

```yaml
api_sync_rules:
  保存:          { path: /api/agents }              # 不写方法 = 任意方法（POST 创建/PUT 编辑）
  确认删除:      { method: DELETE, path: /api/agents }
```

运行时：**点击"保存"前先注册监听，点击后等接口返回**。这一步同时解决两个问题：
- 等到了返回 → 数据已处理完，后续断言时机可靠（替代"傻等 N 秒"）
- 结果记入报告 → "API 返回校验"面板显示方法/路径/状态码/是否收到

### 6.4 DB 落库断言怎么工作

```
需求文档「数据变更映射」表（业务填）
        ↓ AI 翻译 + 对照后端 schema.sql 校验表/列
db-asserts.yaml（AI 产物，工程师确认）
        ↓ 生成器编译成确定性 SQL 常量
db_asserts.py（生成物，运行期只是执行）
        ↓ 场景步骤引用
且数据已保存到 "AGENT_CREATE_001"
```

映射示例：

```yaml
- id: AGENT_CREATE_001
  table: agent_config                      # 物理表名（经 schema 校验存在）
  expect_records: 1                        # 期望查到的记录数
  where:
    - { field: agent_code, from: var, ref: $code }   # 条件值来自场景变量
  assert_fields:
    - { field: agent_name, from: var, ref: $name }   # 断言字段值=变量值
    - { field: enabled, equals: 1 }                  # 断言字段值=固定值
```

**反向断言**：校验失败的场景用 `expect_records: 0`——"保存被前端拦截时，数据库绝不能多出记录"，这是更强的验证。

报告里的「DB 落库断言详情」面板会展示每条断言的完整证据：SQL 语句、参数实际值、期望/实际记录数、每个字段的期望值 vs 实际值 + ✓/✗。

## 七、报告怎么读

一次执行产出 `report/ui-test/report_<时间戳>.html`，从上到下：

| 区域 | 内容 |
|------|------|
| 摘要卡片 | 场景总数/通过/失败/错误/通过率/总耗时 |
| 模块分区（按 feature） | 每个模块的通过率，可折叠展开 |
| 场景详情（点开） | 状态徽章 + **中文场景名** + 场景步骤执行面板（每步✓/✗） |
| DB 落库断言详情 | 每条 DB 断言的 SQL/参数/记录数/字段校验证据 |
| API 返回校验 | 每个写操作的方法/路径/状态码/是否收到响应 |
| 失败场景 | 失败原因 + 完整堆栈 + 失败截图 |
| 元素地图命中报告 | 元素定位健康度（第五节） |

## 八、为什么"别的用例没有 DB 断言"？

这是常见疑问。答案：**不是用例不够好，是设计使然**。

- 读操作场景（列表、筛选、空态、表单打开）——没有写操作，就没有"落库"可断言
- 写操作场景（新增/编辑/删除）——全部有 DB 断言
- 校验失败场景——有反向 DB 断言（`expect_records: 0`）

**原则**：DB 断言只加在"应该产生数据变化"的操作上。无意义的断言只会拖慢测试。

## 九、常见问题速查

| 问题 | 答案 |
|------|------|
| 场景名为什么是"英文（中文）"？ | 英文部分决定测试函数名（稳定），中文部分用于报告可读性 |
| 为什么禁止修改生成的 conftest.py？ | 它是模板产物，下次生成会被覆盖；改动请改模板 |
| 前端改文案了怎么办？ | 改 elements.yaml 对应条目的策略；场景脚本不用动 |
| 业务要写 yaml 吗？ | 不用。业务只填需求文档（markdown），yaml 是 AI 产物 + 工程师确认 |
| 为什么报告里 API 校验显示"未收到响应"却不报失败？ | 同步是 fail-open（避免重复提交），结果如实记录供人工判断 |
