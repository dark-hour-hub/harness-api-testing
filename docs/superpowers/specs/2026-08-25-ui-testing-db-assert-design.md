# UI 测试 DB 断言机制设计（需求文档驱动 + 确定性编译）

> 日期：2026-08-25
> 状态：已与用户逐节确认
> 范围：AgentTest-evalution（harness）UI 测试链路的防假成功断言机制（需求文档模板 / db-asserts.yaml / DSL 扩展 / 生成器编译 / 运行期同步）

---

## 一、背景与痛点

现有 UI 测试断言以「UI 提示」为主（`应看到提示 "<文本>"`），存在两类失真风险：

1. **假成功**：toast 出现 ≠ 数据落库。前端乐观更新、前端校验放行但后端拒绝、后端自身 bug（响应正常但未写入）都会造成 UI 断言通过而数据实际未变更。
2. **提示缺失/延迟**：前端校验拦截、异步写入慢于断言时机，导致断言误报失败或漏报。

复盘证据：`SUMMARY-三线验证复盘总结.md` 中 edit/delete 场景曾因前端校验拦截导致 toast 不出现（提示断言暴露），但反向场景（toast 出现、DB 未写入）提示断言无法覆盖。

**结论**：UI 提示断言证明「用户看到了什么」，无法证明「数据实际发生了什么」。需要贴近真相源的断言层。

## 二、目标与约束（已确认）

| 项 | 结论 |
|----|------|
| 目标 | 防假成功：证明「UI 操作触发了后端数据变更」的业务闭环，重点覆盖创建/编辑/删除等关键写操作 |
| 断言载体 | 需求文档提供「操作→表→字段」映射时用 **DB 断言**（最强）；无映射但有 API 文档时用 **API 响应断言**（兜底）；都无时保持 UI 提示断言（现状） |
| 映射来源 | 业务方按模板提供（业务语言 + 精准表/字段描述），**业务不编写 yaml** |
| AI 角色 | 只做翻译与校验（业务命名→物理表/列），产出草稿；**运行期无 AI**，断言为确定性代码 |
| 人工角色 | 测试工程师只做「确认闸门」：确认 db-asserts.yaml 草稿 |
| 执行层确定性 | 不改「AI 自动改定位+重跑」铁律；断言失败只报告，不自动修复重跑 |

## 三、总体架构

```
业务（markdown 模板）            AI（01 阶段）                测试工程师
─────────────────────        ─────────────────────       ────────────
5 节模板（含数据变更映射表）  →  解析映射表 → 对照 schema  →  确认闸门
  (业务命名表/字段/值语义)        翻译成 db-asserts.yaml      (确认/修正草稿)
                                草稿（对不上输出差异表）          ↓
                                                             确认后入库
                                    ↓
03 场景设计：关键写操作后写 `且数据已保存到 <映射id>`，值来自场景变量 $var
                                    ↓
04 脚本生成：生成器读取 db-asserts.yaml → 编译为确定性 pytest 断言
                                    ↓
05 执行：busy 消失 + 写接口返回后查 DB；失败报告带映射 id + schema 位置
```

**分工铁律**：业务只填模板（自然语言+表格）；yaml 是 AI 产物 + 人工确认；场景保持业务语言；运行期是确定性代码。

## 四、需求文档模板（业务侧填写，5 节）

设计原则：表格化 + 业务语言，强制业务写清楚「变更类型」与「关键字段取值语义」，让 AI 能生成有意义的断言。

```markdown
# UI 测试需求文档

## 1. 模块与版本
| 模块名 | 版本 | 业务负责人 | 日期 |
|--------|------|-----------|------|

## 2. 业务流程（叙述，每流程一段）
[业务用自然语言描述用户操作路径与预期结果]

## 3. 数据变更映射（必填）
| 业务操作 | 涉及表（业务命名） | 变更类型 | 数据变化描述 | 关键字段与取值 |
|---------|------------------|---------|-------------|---------------|
| 新增图书 | 图书表 | 新增 | 新增 1 条记录 | 标题=表单"书名"；库存=0；状态=启用 |
| 借出图书 | 图书表 / 借阅表 | 修改+新增 | 图书表库存-1；借阅表+1 条 | 库存=原值-1；借阅状态=进行中 |

## 4. 字段明细（复杂场景补充）
- 图书表
  - `标题`：来自表单"书名"输入框，新增必填
  - `库存`：新增初始 0；借出时减 1
  - `状态`：枚举{启用,停用}

## 5. 数据约束（可选）
- 唯一约束：图书编码不可重复
- 种子依赖：删除需先停用（复用已有种子数据）
```

模板要点：
- **变更类型列必填**：强制区分新增/修改/删除，杜绝「保存」类模糊描述
- **关键字段与取值**：给出可断言的值语义（初始值/变化规则/来源），而非「表里有记录」
- **字段明细**：说明值来自哪（表单值/固定初始值/计算规则）——断言可靠性的关键

## 五、db-asserts.yaml（AI 产物，人工确认）

AI 在 01 阶段从模板第 3/4 节解析，对照 `schema.sql`/实体类校验后生成草稿：

```yaml
db_asserts:
  - id: AGENT_CREATE_001
    ui_action: 保存新增智能体表单
    table: agents
    expect_records: 1
    where:
      - { field: agent_code, from: var, ref: $code }   # 值来自场景变量
    assert_fields:
      - { field: name, equals: "新增智能体A" }
      - { field: enabled, equals: 1 }
    sync: { api: "POST /api/agents", status: 200 }     # 断言前同步点（路径来自 API 文档链路）
    schema_ref: schema.sql#agents
```

校验规则：
1. 业务表名 → 物理表名映射必须经 schema 校验存在
2. 业务字段 → 物理列映射必须经 schema 校验存在
3. 校验不通过 → 输出「业务命名 vs 物理命名」差异表，交由人工确认，**不静默猜测**
4. 校验通过 → 草稿入库（测试工程师确认后）

置信度分级（决定确认强度）：
- 需求文档明确提到表/字段 → 高置信，快速确认
- AI 推断（文档只描述行为）→ 必须逐条确认
- 文档完全未提数据 → 该操作降级为 API 响应断言，不硬造 DB 映射

## 六、DSL 扩展（3 个新元素）

| 元素 | 示例 | 说明 |
|------|------|------|
| 场景变量 | `令 $code = "${rand:8}"` | 声明变量，输入步骤与映射 where 共用 |
| 映射引用 | `且数据已保存到 AGENT_CREATE_001` | 显式声明此步骤需要 DB 断言 |
| 值引用 | `在 "编码" 输入框中输入 $code` | 变量在步骤中展开 |

规则：
- 场景变量仅限当前 Scenario 作用域
- 映射引用步骤必须出现在对应写操作步骤之后
- 引用缺失 / 变量未声明 / 映射 id 未定义 → 生成期报错中止

## 七、生成器编译机制（确定性）

`generate_playwright.py` 扩展：读取 `db-asserts.yaml`，把映射引用步骤编译为：

1. 等 busy 指示器消失（business.yaml 的 `busy_indicators`）
2. `page.wait_for_response` 等写接口返回（`sync.api`，路径来自 API 文档链路，状态码校验）
3. pymysql 只读 SELECT（WHERE 用场景变量实际值）
4. 断言记录数（`expect_records`）与字段值（`assert_fields`）

**生成期静态校验**（产物即证据）：
- 映射 id 未定义 → 报错
- 表/字段在 schema 中不存在 → 报错
- 变量未声明 → 报错
- 全部通过才进入执行阶段

禁止项：
- 禁止在场景/脚本中硬编码物理表名与 SQL
- 禁止生成器之外手写 DB 断言代码（断言必须由生成器统一编译，保证口径一致）

## 八、断言时机与降级链

### 断言时机（防误报）

```
操作步骤 → 等 busy 消失 → wait_for_response(写接口) → 查 DB → 断言
```

与重构设计「API 级同步」一致：先等 UI 就绪，再等后端请求返回，最后查数据事实。不采用轮询重试与固定 sleep（避免引入噪音与回到固定等待老问题）。

### 降级链

```
需求文档有映射        → DB 断言（最强）
无映射但有 API 文档   → API 响应断言（兜底）
都无                 → UI 提示断言（现状）
```

## 九、失败报告与追溯

- DB 断言失败 → 失败截图（现有机制）+ 错误信息含映射 id、`schema_ref`、实际查询 SQL 与期望/实际值
- 报告错误信息可直接追溯到需求文档对应条目与 schema 位置
- 归属 post-run-analysis 分析流程（非被测项目 bug 类：映射错误/需求文档错误/schema 变更）

## 十、人工参与模型（确认闸门，不做生产）

| 环节 | 人工角色 | 频率 |
|------|---------|------|
| 业务填需求模板 | 业务方生产（唯一生产方） | 需求变更时 |
| db-asserts.yaml 草稿 | 测试工程师确认/修正 | 每需求文档一次 |
| 业务命名 vs 物理命名差异 | 测试工程师裁决 | 校验不过时 |
| 失败复盘/经验回写 | 确认闸门（既有流程） | 有失败时 |

## 十一、与现有链路及重构规划的关系

- 复用：03-api-docs 链路（写接口路径）、business.yaml 配置层（busy 指示器）、现有截图/报告机制、post-run-analysis 归因流程
- 对齐：重构设计第八节「API 级同步」——本设计是其「等待」语义的「断言」升级
- 落点：作为重构设计**阶段 3「数据闭环」的扩展子项**实施；未来映射可平滑迁入 `ui-profile/` 配置层（与「项目差异全进配置层」方向一致）
- 独立可用：本机制不依赖重构设计其他阶段，可单独实施

## 十二、明确不做（YAGNI）

- 不做运行期 AI 翻译/猜测（映射在生成期一次性编译，运行期确定性）
- 不做 DB 写入类断言（只读 SELECT；写入由被测系统自身完成）
- 不做字段级全量断言（只断言关键字段，防 schema 耦合）
- 不要求业务编写 yaml / SQL / 物理表名（业务语言，AI 翻译）
- 不轮询重试 DB 查询（靠 busy + API 同步保证时机）
- 不做 AI 自动修复断言失败并重跑（保持执行层确定性铁律）
